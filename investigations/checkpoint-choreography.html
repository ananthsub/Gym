Checkpoint Choreography

Who calls what, in what order, with diagrams · Aug 25, 2026 · storage design and rationale live in the companion, Tokidcap Two Clocks

This page walks the full checkpoint save and the full restore, process by process, down to individual calls: the complete wire trace lists every request Gym makes or receives, what is durable when it returns, and what a crash immediately afterward means. The stated-assumptions register lists every property the design depends on. Status discipline, enforced after an adversarial audit: a mechanism is marked as existing only when it exists on main or the session-state-prototype branch; everything else belongs to a G-phase or a named PR, and the audit-resolutions section records every finding the review produced. It also answers the recurring implementation questions: how the retry hint is computed, how in-flight requests are counted without races, why model call ids are never reused, why rollouts do not need to return to the same node, why the protocol is two-phase, and how a dispatch is recognized as a resume.

The processes and who commands whom

The SingleController is a Ray actor in NeMo RL. It creates one or more NemoGym actors, also Ray actors, one per Gym node. Each NemoGym actor launches the Gym servers — model server, agent server, resources servers — as OS subprocesses on its own node, so the actor and its servers share a filesystem. The model server runs N uvicorn worker processes behind one port. The vLLM generation workers are separate Ray actors owned by the SingleController. TransferQueue is a set of Ray actors holding token data in memory. The rule that keeps the choreography simple: each process commands only the processes it created. The SingleController commands the trainer, TransferQueue, the vLLM workers, and the NemoGym actors. Each NemoGym actor commands its own Gym servers over localhost HTTP. The agent server commands the resources servers, because only the agent knows when a rollout reaches a tool boundary. Nothing else commands anything.

The two planes of the model server

The adversarial audit found the design's largest structural gap here, so it gets its own section. The model server serves two kinds of traffic, and everything earlier in this document was specified for only the first. The policy plane is the agent's own generation — the calls that produce training tokens. The environment plane is model inference made by the environment itself: LLM judges called at verification, user simulators and tool simulators called inside tool execution. Roughly a third of the resources servers call models, and Gym's client plumbing routes their calls through the same capture-prefixed model server the checkpoint pauses. Four correctness failures follow if the planes are not separated:

  1. A rollout that finishes during drain must run verify(); its judge call hits the paused model server, exhausts the internal client's budget, and the judge failsafe converts a completing rollout into a reward-zero failure row — a durable side effect that also falsifies "prepare creates nothing durable". Every checkpoint would silently corrupt completing rollouts.
  2. A user or tool simulator calls a model inside tool execution — inside the very step drain waits on — while the sentinel blocks that inner call: drain waits for the tool, the tool waits for unpause. The rollout burns the full deadline, parks mid-tool, and after resume the timed-out inner call surfaces as an error-string tool output the agent feeds to the model as content: checkpoint-injected trajectory corruption.
  3. Agents like tau2 and Claude Code interleave policy-chain and simulator/subagent-chain calls under one rollout id. The anchor, masking, and finalization rules are defined over a single chain; sibling-chain rows are neither before nor beyond the anchor, and no rule says whether simulator tokens are masked, retired, or trained on.
  4. A turn containing both an agent call and a user-simulator call breaks the boundary record's single model_call_id join, and the simulator's message fits neither "output items" nor "tool results" — rebuild would silently drop the last user turn.

The fix is one design element: an actor tag on every model-server request, set at admission. Three values — policy, environment, internal-eval — carried as a request header by Gym's own clients and defaulted by route class for external traffic. Everything then scopes by tag. The pause sentinel gates policy admissions only; environment traffic passes during prepare (a judge finishing a rollout, a simulator inside a draining tool), with an explicit fail-fast policy for it during the brief commit window if the sink barrier is engaged. The hold-versus-503 choice keys on the tag plus route class: capture-prefixed external traffic holds first; marked-internal traffic gets an immediate 503 with Retry-After, and the native client treats it as an implicit drain signal. In-flight counting counts per plane, and "quiet" for the TQ save means the policy plane is quiet. The ledger scopes chains by tag: parent resolution, the anchor, masking, and the finalizer's per-group assembly operate on the policy chain; environment-plane calls are captured (they are still exact tokens someone may want) but never enter a training row, and their staged rows are swept with the rollout. The boundary record's join key is the last policy-plane call of the step, and tool_results is defined to carry every non-policy-authored conversation item of the step — tool outputs, simulator messages, observations. Two further rules ride along: capture-route admission rejects n>1, and requests from in-process library harnesses (tau2, langgraph, aviary — loops in third-party code, HTTP stacks that are not Gym's client) are treated as the blackbox audience: their parked state is quiet-at-the-model-server.

Save, phase 1: prepare

The prepare phase brings the system to a quiet, describable state. It creates nothing durable, so it can be aborted at any point by resuming the pumps and the pause flag.

What a boundary is, and how its marker is persisted

The agent server's /run loop repeats four steps: send the conversation to the model server; receive the response; execute the response's tool calls against the resources servers; append the tool results to the conversation. A tool boundary is the moment after appending the tool results and before sending the next model call. At that moment, and only at that moment, the conversation and the environment agree: every tool effect that has happened is also written into the conversation. The other moments are not boundaries for concrete reasons — mid-generation, the response is not yet committed anywhere; mid-tools, the environment has changed in ways the conversation does not yet show. Boundary k is this moment after the k-th round of tool execution. Boundary 0 is the moment after seeding, before the first model call — it doubles as the rollout's arrival marker (wire-trace row A4).

Before the record's fields, the file layout it lives in — this is the first place the session-state directory appears, so it is defined here. Every rollout owns one directory on the Gym node's local disk, with exactly two writers who never share a file:

Today the capture store writes flat files <root>/<rid>.tokens.jsonl whose rows carry full token arrays, and the session store writes a per-rollout directory with boundaries.jsonl and <server>.snapshot.<idx>.json — separate roots, no shared directory. The prototype's docstrings also place both stores on shared storage; this design deliberately moves them node-local with pack-at-cut, and that is a change, not a description. The two JSONL files are independent — different processes, different flocks — and they are joined by the ledger's primary key, never merged: on capture-prefixed routes the model server echoes its minted model_call_id on the response — a G2 addition; no header echo exists today — and the agent stores it in the boundary record. Commit-before-release makes the dangerous direction impossible by construction — the agent can only ever possess a call id whose ledger row is already durable, so no boundary record can reference a call that does not exist. This resolves a redundancy an earlier draft carried: the boundary record does not store the model's output items, because calls.jsonl already stores them; the record stores only what the ledger cannot yet know. Large environment states do not inline. For those, the export writes a snapshot file, one per (server, boundary), placed by atomic rename — and the ordering is fixed: snapshot first, boundary record second. A record's existence therefore guarantees its snapshot's existence; a crash between the two writes leaves an orphaned snapshot, which is harmless. Sandbox-backed servers store a reconnect descriptor in place of state. Torn final lines are dropped by readers, the same rule as every append-only file in this design.

Persistence location follows the storage tiering: the session-state directory lives on node-local disk beside the capture ledger, and both file families are packed into the same cut archive (wire-trace row E3). A resumable boundary is one whose record exists and whose environment can actually be restored: stateless servers make every boundary resumable; stateful servers require the snapshot (or inline state); sandbox servers additionally require a reconnectable provider and a live sandbox at restore time. Conversation rebuild at resume uses both files: the ledger chain through the anchor call supplies the conversation, and the anchor boundary's tool_results are appended after it. The rollout's anchor — the point restore resumes from — is computed at pack time, after the population parks: the newest resumable boundary whose model_call_id matches a ledger row included in this cut's sync, with the witness fields verified; boundary 0 is anchor-eligible with a null model_call_id and anchors the rollout at its root. The pack syncs calls.jsonl before boundaries.jsonl for each rollout, so the archive preserves the same invariant the live files have: every boundary in the archive has its call in the archive. Only the agent server ever writes boundary records, because only it knows when tools finished; the actor reads them at pack and restore; the model server never touches them.

When the agent and resources servers save — the timing rule and its edge cases

The timing rule first, because everything else follows from it. Agent servers and resources servers never checkpoint as processes, and there is no phase in which "the Gym servers save". The boundary record plus environment snapshot is a per-rollout save that already happens during normal operation, every time a rollout finishes a round of tool calls. The drain flag does not introduce a new save path; it stops each rollout at the next point where that existing save has just run. What the checkpoint adds globally is only: set the flags, wait for the population to park, pack the files. The edge cases are what happens to individual rollouts that are not at a convenient point when the flags go up.

  1. A rollout is mid-tool-execution and the tools are slow. Example: a swebench rollout starts a four-minute test run, and the drain deadline is sixty seconds. Its boundary record for this step never commits. Its anchor stays at the previous boundary. The model call whose tools were running has a committed row in the ledger, but it lies beyond the anchor, so resume masks it and regenerates that call. For a resources server holding state in memory, this is consistent: restoring the previous snapshot replaces the state wholesale, which rewinds the half-applied tool effects. For a live sandbox it is not consistent: the sandbox's filesystem already contains the partial effects, and the reconnect descriptor points at that same sandbox. Until sandbox filesystem rewind exists, the prepare report must mark such rollouts non-resumable, and restore retries them from the beginning. This is the sharpest edge case in the design, and it is per-rollout, not global.
  2. Why the drain flag, and not the held connection, is the primary signal for Gym's own agents. Gym's internal HTTP client retries a generic failure three times with fixed half-second sleeps, retries disconnect-class errors without limit, and rides aiohttp's default five-minute total timeout — so a native agent parked on a held connection eventually aborts its rollout via the total timeout, and a middlebox that resets the held connection sends it into unbounded reconnect retries instead. The agent-side drain flag avoids all of this: the agent checks the flag before sending, and parks without ever opening the connection. The model-server path remains for external harnesses that cannot see the flag, for in-process library harnesses (tau2, langgraph, aviary — a third audience whose loops run third-party code and whose HTTP stacks are not Gym's client; their parked state is quiet-at-the-model-server), and for the race window where a native agent checked the flag just before it was set. A raced native request must not be left on the hold: the model server answers marked-internal requests with an immediate 503 and Retry-After, and the native client treats a paused response as an implicit drain signal — park and re-check the flag, never fail the rollout. For that audience the priority inverts: hold the connection first (their SDKs wait minutes for a response but retry errors only about twice), and answer 503 with Retry-After only past the hold budget.
  3. The drain forces a snapshot even when the cadence knob would skip it. During normal operation, snapshots may run on a cadence (every k-th boundary) because some environments are expensive to export. If the drain honored the cadence, a rollout could park at a boundary whose record exists but whose snapshot does not, and its anchor would silently regress to the last snapshotted boundary. The rule: a boundary reached under the drain flag always exports, cadence ignored.
  4. A rollout parked before its first tool call has no session to export. Nothing is wrong: there is no environment state yet, the seed is the task row, and its anchor is the root. The export step is skipped, not failed.
  5. A rollout on a resources server that does not support export (supports_session_state() returns false) parks normally and its conversation is saved normally, but its environment cannot be restored. The prepare report marks it non-resumable and restore retries it from the beginning — a rule the (future) prepare report enforces. The prototype today does something different: it treats such servers as stateless and resumes anyway, which is correct only when the server truly holds no state; the report-enforced demotion is what makes it safe in general. Per-server, recorded per rollout at cut time; one unsupported environment never degrades the deployment.
  6. A rollout whose model response had no tool calls finishes instead of parking. Its /run returns during prepare, it becomes complete-and-unconsumed, and it appears in the manifest as such. No boundary machinery is involved.
  7. A periodic checkpoint kills nothing. The parked /run loops stay alive through commit, holding their open HTTP requests, and continue the moment the flags clear. The resumable-/run restore path executes only after a shutdown or a crash, when the processes are actually gone.
  8. The cut archive packs both file families, and anchors are computed at pack time. The per-rollout ledger files and the session-store records and snapshots travel in the same archive. After the population has parked, the actor computes each rollout's anchor as: the newest boundary record that has its snapshot (or needs none, for stateless servers), whose model_call_id matches a ledger row included in this cut's sync. Computing anchors before the population parks would race the very saves the drain exists to finish.

Save, phase 2: commit

The commit phase writes everything. The trainer save has been running since prepare began, because it touches only trainer state. Three saves run in parallel; they cannot conflict because generation is paused, so nothing writes to TransferQueue, and the rollout files never touch TransferQueue at all. The completeness marker is written last.

Restore

The generation workers during checkpoint and restore

The vLLM generation workers appear thin in these diagrams, and the reason should be stated rather than left implicit: at commit time they have nothing of their own to save. Their weights are saved by the trainer's checkpoint. Their KV cache is recomputed from token ids at restore, so it is discarded on purpose. The token deltas they produced are already inside TransferQueue, which has its own snapshot. Their roles in each phase are therefore small and specific. During prepare they do one thing: finish the generations already running, each of which stages its tokens and returns its coordinates exactly as in normal operation. Nothing needs to cancel the stragglers that miss the deadline — their staged rows become orphans that the resume path masks — though the SingleController may abort them to free GPU time sooner. During commit they are idle; the one optional command they can receive is the sink barrier, where the SingleController tells its own workers to hold staging puts while the TransferQueue snapshot runs and releases them when it completes. Whether that barrier is needed depends on whether TransferQueue's save is safe under concurrent puts, which is an open verification item on the TransferQueue side. At restore, the SingleController restarts the workers with the restored weights and reinstalls the capture sink during setup. On the first resumed call a worker's prefix cache is empty, so it fetches the parent chain from the restored TransferQueue rows once, splices it as the exact prompt prefix, and proceeds as in normal operation. All commands to the workers come from the SingleController; none pass through Gym.

The export/restore API

These are the routes and hooks the diagrams reference — step ⑧ of prepare and step ⑦a of restore. They exist today on the session-state-prototype branch, defined on SimpleResourcesServer, so every resources server inherits the routes automatically. A server opts in by overriding the hooks.

  • supports_session_state() → bool — class hook, default False. A server that returns False keeps whole-rollout retry: its rollouts restart from the beginning instead of resuming. Support is a property of each environment server, not of the deployment.
  • export_session_state(session_id) → dict | None — class hook. The server returns a JSON-serializable snapshot of one session's state. workplace_assistant serializes the pandas DataFrames it holds in memory; blackjack returns its random-number-generator state; a sandbox-backed server returns a reconnect descriptor such as the sandbox id, not the sandbox contents.
  • restore_session_state(session_id, state) — class hook. The server rebinds a previously exported snapshot to the session. A freshly started server process holds no sessions in memory; this call recreates the entry.
  • POST /ng-session/export — HTTP route on every resources server, called by the agent server. The route runs the export hook and writes the snapshot into the session store; snapshot before the boundary record that references it, so a record's existence guarantees its snapshot's existence. Cost model, because export can be expensive: the boundary record is thin (ids, tool results, usage) and is written at every boundary — cheap and non-negotiable. The snapshot is the costly part and is cadence-controlled — today an agent-side knob (session_state_snapshot_every_n_steps), per-server override as a G3 refinement: export every boundary (maximum crash freshness), every k-th boundary, or only at drain (zero steady-state cost; environment freshness limited to planned cuts). Drain always forces one final export regardless of cadence — unimplemented today, part of G2/G3. A skip-when-unchanged optimization needs one prerequisite first: in the prototype, a server declining to export causes the agent to skip the entire boundary record, losing that step's conversation delta — the record-without-snapshot path must exist before any skipping is safe.
  • POST /ng-session/restore — HTTP route. The agent server calls it during a resumed /run, before re-entering the loop. The route accepts the state in the request body or loads the stored snapshot, then runs the restore hook.

Session identity needs no new plumbing in either direction. The session id travels in the same session cookie the tool calls already use, and it is computed from the rollout id — so a resources server process started fresh after a restore derives the same session id, and the restore lands in the right session.

How boundary markers map to sandbox state

A boundary record never contains sandbox state. For a sandbox-backed server, the snapshot slot holds the output of ConnectableProvider.serialize_handle() — and reconnectability is not a new flag but an existing protocol in nemo_gym/sandbox/providers/base.py: a provider that implements ConnectableProvider can serialize a handle to a descriptor and later connect(descriptor) back to the live sandbox. Today only OpenSandbox implements it, because it has an external control plane a new Gym node can reach. Local providers — Apptainer, Docker, enroot — run the sandbox as a process with no external control plane, do not implement the protocol, and their boundaries are therefore non-resumable: the rollout restarts from scratch, safe and explicit. The resumability rule is mechanical: a boundary on a sandbox-backed server is resumable exactly when the provider implements ConnectableProvider and connect() succeeds at restore. The forward-compatibility seam is the protocol itself: a sandbox-server control plane (the PR 2085 direction) makes local providers implement ConnectableProvider, which changes which rollouts are resumable without changing a single interface — the descriptor, the liveness check, and the boundary record schema all stay as they are. Token-level and conversation-level resume never depend on any of this; only environment restoration does.

Two custody questions, answered

Is a marker needed when Gym receives the rollout, before any model-server record exists? Yes, and it is not a new mechanism: it is boundary record 0, written at row A4, immediately after seeding and before the first model call. Without it, a rollout killed between seeding and its first commit is invisible to Gym-side restore — which is acceptable for the conversation (the SC re-dispatches from the task row) but not for resources: a sandbox allocated during seeding would exist with no record pointing at it. Boundary record 0 closes that window for every crash after A4. The window between A3 and A4 — sandbox allocated, record not yet written — cannot be closed by our own records at all, which is why assumption 6 requires sandboxes to be tagged with {run_id, rollout_id} at allocation and reaped by a tag-based janitor that does not depend on our files.

Where do sandbox ids live? One custody chain, one owner at each step, and two parties that never see them. The resources server allocates the sandbox through Gym's sandbox API — which today stamps team/user/workload/run attribution on OpenSandbox only; stamping the rollout id everywhere is the G4 extension — and holds the live handle in memory (A3). At every boundary, its export hook returns the reconnect descriptor — the sandbox id and connection details, not the sandbox contents — and the descriptor is written into the session store's snapshot, referenced by the boundary record (A4, B8). The session store's files are packed into the cut archive with everything else (E3). At restore, the descriptor comes back through /ng-session/restore, and the resources server — the only component that ever interprets it — reconnects and verifies liveness (F6). The agent server carries the descriptor as opaque bytes inside records it owns; the actor packs and extracts files it never parses; the SC and the model server never see sandbox ids at all.

Stated assumptions

Everything above is sound if and only if these hold. Each is either a property to verify or a rule to enforce; none is optional.

  1. Stateless conversation protocol. The harness re-sends the complete message list on every model call. Parent resolution, per-call transcript capture, and resume-by-re-dispatch all stand on this single property.
  2. Ordering invariants. Stage before commit at the worker; commit before release at the model server; snapshot before boundary record at the agent; files before sidecar at the cut; marker file last at commit. Every crash-consequence cell in the wire trace derives from these five orderings.
  3. TransferQueue. Puts are idempotent by sample key. save_checkpoint/load_checkpoint round-trips the staging partition. Whether the save is safe under concurrent puts is unverified — the sink barrier exists to make the question moot.
  4. Filesystem. Atomic rename on local and shared filesystems; fsync durability as configured; flock honored between the model server's worker processes — they share one node, so same-node advisory locking suffices, and no cross-node locking is ever required.
  5. Identity. Session ids and worker affinity are pure functions of the rollout id. Call-id collisions under uuid4 are ignored as negligible. Internal clients send a logical request id for retry deduplication, and the model server echoes the minted call id on capture-route responses — the boundary join key is the ledger's primary key, not a secondary id. Parent resolution treats candidate rows with identical staging digests as a single candidate — this covers a double-recorded response from an external harness retry, which carries no logical id.
  6. Sandboxes. Every sandbox is created through Gym's own sandbox API (nemo_gym/sandbox), whose attribution layer resolves team/user/workload/run metadata — wired up today by exactly one provider, OpenSandbox, where it becomes queryable Kubernetes labels; the other providers merge nothing yet. The G4 rule is therefore two keys of work, not one: wire attribution through every provider, and add the attempt-scoped rollout_id to the metadata at allocation. The janitor is then a Gym-side sweep, not an external hope: query the provider by run label, and reap every sandbox whose rollout is neither live nor referenced by a live checkpoint. For providers that cannot list by label, a durable allocation registry — append-only, written by the sandbox API at creation — is the fallback. Sandbox lifetime must exceed the maximum expected restore gap; reconnect-by-id is supported and verified at restore; filesystem rewind is not assumed — which is exactly why mid-tool sandbox rollouts are non-resumable.
  7. Process management. The NemoGym actor runs with max_restarts=0: every restart is deliberate and SC-driven. The SC is the only dispatcher of rollouts.
  8. Blackbox harnesses. Capture works for them. Partial resume is not part of the base design, because their loop state lives outside Gym — in the base design their rollouts restart from scratch. There is a harness-specific extension path that requires no architectural change: keep the harness's Gym-provisioned sandbox alive across the gap (its descriptor is in boundary record 0), reconnect at restore, and re-launch the harness using its own persistence — Claude Code and Codex both keep session state on the sandbox filesystem and support native resume. The relaunched harness re-sends its conversation, and fingerprint resolution admits it against the ledger exactly like any continuing call. What makes this an extension rather than the default: it depends on each harness's resume capability and on the wrapper knowing how to invoke it, and the harness's in-flight model call at the kill is always lost and regenerated.
  9. No clock dependencies. No step relies on synchronized clocks. Ordering comes from write order on single files; correlation comes from ids.
  10. No derived state in the checkpoint. KV caches, lineage caches, resolver cursors, and worker prefix caches are all rebuilt from the logs. If a piece of state can be recomputed, it is never saved.
  11. Buffered SSE. Streaming responses are synthesized from a fully buffered backend completion, which is what lets commit-before-release and the header echo survive streaming clients. This is load-bearing: a true token-streaming backend would deliver a prefix the client has seen before any row commits, forking the harness's history from the ledger. Hold budgets are sized from streaming clients' time-to-first-event timeouts, not the ten-minute full-response number.
  12. One SingleController, leased. Exactly one SC is alive at a time, enforced by a lease; the actor's checkpoint operations serialize.
  13. Actors die with their owner. NemoGym actors are non-detached and take their subprocess groups down; a new SC tears down survivors before restore.
  14. Actor tags on model traffic. Every model-server request is tagged policy / environment / internal-eval at admission; pause, counting, chains, anchors, and finalization scope by tag (see the two-planes section).

Rules the adversarial audit added

Four independent reviews (code-grounding, state-schema consistency, mechanism-by-actor-class coverage, crash-and-race interleavings) produced 74 findings. The status corrections and the two-planes section absorb the largest ones; the remaining accepted rules are recorded here so none lives only in a review thread. Each is binding on the implementation.

Checkpoint and restore integrity

  1. TQ snapshots are content-addressed: each save_checkpoint writes to a fresh path, never mutating bytes an existing training_info.json binds; restore loads by the bound digest, never "latest". A crash mid-save can then never corrupt the previous checkpoint.
  2. Checkpoint ordering is by the step number encoded in the directory name — never by mtime, which would be a clock dependency the assumptions register forbids.
  3. After the atomic rename, fsync the checkpoint root directory before treating commit as complete; rename makes a directory visible, not durable.
  4. The actor packs to temporary names and renames archive, index, and manifest into place; each commit attempt uses a fresh gym_dir, so an abandoned half-pack is never re-entered.
  5. The member index drops any boundary row whose model_call_id is not among this cut's synced calls — the anchor filter promoted to an archive filter, closing the window where a call commits between the pack's two file reads.
  6. Restore assignments include complete-but-unfinalized rollouts as extraction-only members: their ledger files are extracted so the manifest route can serve finalization, but no /run is dispatched.
  7. Retirement is fenced from prepare through commit: in-flight retires are joined before packing begins, and the pack excludes a rollout entirely if any of its files vanishes mid-copy — all files or none.
  8. The TTL sweep applies the same checkpoint-pin predicate as retire, re-read from the newest manifest at reap time; the janitor re-checks the newest manifest after selecting victims.
  9. Retirement triggers on terminal disposition — consumed, failed-final (judge-failed rows included), or superseded by a new attempt — not on trainer consumption alone; superseded attempts' staged TQ rows are swept by attempt id, closing the orphan accumulation the checkpoint would otherwise re-persist forever.
  10. Staging-key reconciliation runs after extraction (or against an expected-count the Gym manifest carries), and every assigned rollout's anchor chain is verified against restored TQ before dispatch, demoting to fresh retry on a miss — never surfacing as a serving error after the environment is already rebound.

Pause, drain, and quiescence

  1. Commit's resume step clears all three controls: the model-server sentinel, the agent-server drain flag (a flag file, same idiom), and the worker sink barrier. Barrier release is also unconditional in abort and in SingleController startup, so a crash between engage and release can never wedge generation.
  2. Model-server startup clears any stale sentinel and counter files; counter files carry the worker's incarnation (pid + start time), and the status route ignores counters from dead incarnations — a crashed worker can never wedge quiescence.
  3. In-process counter updates are atomic with respect to the event loop: no await between read and rename, or a per-worker lock — otherwise concurrent coroutines lose increments and a zero count lies.
  4. Prepare must await in-flight finalizations, not only generations, before the TQ save — the sink barrier gates worker staging, not the finalizer — and the finalizer publishes before it clears, so a torn snapshot re-runs instead of stranding a group.
  5. POST /control/pause carries the deadline; Retry-After is computed from it during drain.
  6. Boundary records with empty tool_results are permitted at any model-call edge with no pending tool calls, so chat-only and reasoning-only stretches anchor at their latest call instead of regenerating durably committed work; for gymnasium-style loops the boundary is "after the turn's environment interaction completes", with the observation as the tool-results equivalent.
  7. Seeding is idempotent per session key: a retried /seed_session reuses the session's existing sandbox instead of allocating a second one.
  8. The resume decision table's refuse-loudly cell is scoped to marker-capable dispatchers; eval dispatch (no SingleController, deterministic rollout ids, legitimate re-runs) clears-and-reseeds as the prototype does, or uses a separate state directory. Drain, status, and the prepare report are scoped to the checkpoint's rollout-id set so mid-training validation traffic neither parks nor pollutes the report.

Process and topology

  1. NemoGym actors are non-detached: owner death kills them and their subprocess groups, and a new SingleController tears down any survivors before restoring — two nodes must never extend the same attempt.
  2. Exactly one SingleController is alive (a lease, not an assumption); the actor's checkpoint tasks serialize so a second prepare queues rather than interleaving with a running pack.
  3. MCP-exposed tools mean blackbox sandboxes call resources servers directly, across the cluster boundary, during pause and pack — the topology diagram's "agent server is the only caller" holds only for non-MCP deployments, and the blackbox-resume extension must re-issue MCP endpoints and tokens at reconnect because the sandbox baked in the dead node's URL.
  4. The commit-before-release guarantee is a process-crash argument: under power loss, a durable boundary can outlive a page-cached ledger row. It is harmless because restore reads only packed archives, whose pack does its own synced-range filtering — a dependency now stated rather than accidental.

The changes Gym needs, in sequence

Four phases. Each is independently shippable, each is useful on its own, and no later phase changes an interface an earlier phase introduced — that is the criterion the sequencing was chosen by.

  1. G1 — token-level checkpointing, no environment state. Model server: the B′ row (input delta + output items merged into the ledger commit), self-healing appends, /control/pause, /control/resume, /control/status with the sentinel file and per-worker counter files. NemoGym actor: fence / prepare_checkpoint / commit_checkpoint(gym_dir) / abort / restore(gym_dir, ids) / resume, the pack-and-extract path, the Gym-internal manifest. SingleController: the two-phase sequence with the marker-last commit. This phase alone makes killed rollouts resumable for stateless environments, and it touches no resources server and no agent beyond re-dispatch.
  2. G2 — turn-level: boundary records. Model server: echo the minted model_call_id as a response header on capture routes. Agent servers: the thin boundary record (model_call_id, tool_results, usage, agent_state, witness fields) written per boundary into boundaries.jsonl; the drain flag checked before each model call; /control/status reporting per-rollout loop position; the resume decision table on /run entry. This buys back the one-call freshness window and anchors resume at boundaries.
  3. G3 — environment state. Resources servers: the /ng-session export/restore routes and hooks (already in the session-state prototype), the snapshot cadence knob with forced-export-at-drain, and the per-server audit — incremental and safe by default, because supports_session_state() defaults to false and an unaudited server simply keeps whole-rollout retry. No audit gates G1 or G2.
  4. G4 — sandboxes. The one-key attribution extension (attempt-scoped rollout id in sandbox metadata), the label-query janitor, the liveness check at restore, and the per-provider reconnectable capability bit. Later, without interface changes: a sandbox-server control plane for local providers (the PR 2085 direction) flips capability bits, and harness-native blackbox resume (assumption 8's extension) becomes possible per harness.

Implementation specifics

How is the Retry-After value chosen?

The value is a polling hint, not a promise. A client that retries early receives another 503 with a fresh value. A client that retries late finds the server already resumed. Nothing breaks in either case. The server can therefore use simple estimates: during the drain phase, the time remaining until the deadline the SingleController passed in; during the save phase, a running estimate from the durations of recent checkpoints; absent both, a fixed ten seconds. The deadline bounds how long the model server waits for running generations before they are abandoned. The Retry-After value uses the deadline as an input, but the two are not the same number and do not need to be.

How are in-flight requests counted, and is there a race?

There is a race in the obvious design, and an ordering rule removes it. The obvious design has a request check the pause flag first and become visible later, when it writes its intent line to the rollout file. Suppose a request passes the pause check just before the sentinel file appears. The status poll counts intent lines without commit rows, sees zero, and the actor proceeds — while that request is still on its way to vLLM. The fix is publish-then-check: on entry, the worker first makes the request visible, then checks the pause flag, and a request that finds the flag set withdraws. Visibility is a per-worker counter file, updated by atomic rename on entry and exit; the status handler sums the counter files and cross-checks the dangling-intent count from the rollout files. With that ordering, a zero count means no request has passed the entry point. There is also a backstop that makes the count a scheduling aid rather than a safety mechanism: a call that commits before the file pack is included in the checkpoint, and a call that commits after the pack only writes rows the manifest never references, which resume masks. A missed count can waste a little work; it cannot corrupt the checkpoint.

Are model call ids ever reused, and does that clash with the middleware minting them?

Ids are never reused, and no clash exists, because the three situations that look like reuse are each handled by a different key. First, client retries: when a network failure hides a response that was actually committed, the retried request would mint a second id and commit a second row. The dedup key for this is the logical request id header the caller supplies; the middleware sees an existing commit for that logical id and returns the recorded response instead of generating again. Second, resume: the continued rollout's next call is a genuinely new call. The middleware mints a fresh id for it, and its parent pointer references the anchor's old id. Old ids are read from the file during resolution; they are never minted again. Third, double dispatch: if a confused restore dispatched the same rollout twice, the two attempts would write under attempt-scoped rollout ids — {group}_g{i}_a1 and {group}_g{i}_a2 — so their files and staging keys never collide, and the SingleController's ledger decides which attempt counts.

With multiple NemoGym actors, must rollouts return to the same node?

No, and the design guarantees the wrong-shard problem cannot occur, because no actor ever "loads a shard". Three properties make location irrelevant. Each rollout's file is self-contained: everything needed to resume that rollout is in its own rows. The archives live on the shared filesystem under an index keyed by rollout id, so any actor can find any rollout's segments regardless of which node packed them. Session identity is computed from the rollout id, so a resources server on a different node derives the same session key, and TransferQueue staging keys are cluster-global. Restore therefore works by assignment: the SingleController assigns each resumable rollout to whichever actor exists now, and each actor extracts exactly its assigned members from whichever archives hold them. A rollout resumed on a different node loses only vLLM cache warmth, which costs one TransferQueue prefix fetch on its first call.

Should the protocol be two-phase?

Yes. Phase one, prepare_checkpoint(deadline): fence the pumps, pause admission, drain or hit the deadline, and collect from each actor only per-rollout status — resumable or not. Everything else Gym knows stays inside Gym. Prepare creates nothing durable, so aborting it costs one resume() call and a deleted temporary directory. Phase two, commit_checkpoint(gym_dir): each actor writes everything it needs to restore — archives, anchors, its own manifest — into the subdirectory it was handed; the SC binds only the path, runs the parallel saves, writes the marker last, renames atomically, resumes. The SC cannot know the individual states its subsystems save, so the contract never asks it to. This is not classic distributed two-phase commit, and it does not need to be: the commit point is a single atomic rename performed by one process, so no distributed agreement is required. The phases exist for two other reasons. A failed or timed-out prepare aborts cheaply, leaving the previous checkpoint as the newest complete one. And the expensive trainer save overlaps the prepare phase, because it depends on nothing prepare does.

How does the pause reach a blackbox harness like Claude Code or Codex, running in a sandbox on a separate CPU cluster?

The drain flag does not reach them, and nothing needs it to. The flag is a check Gym's own agent loop performs before sending its next model call. Claude Code, Codex, and OpenHands run their own loops inside their sandboxes; Gym's wrapper agent server launched the harness and waits for it to finish, but it does not drive the loop and cannot park it. The one point Gym controls is the point every harness must pass through: the model server, which the harness reaches because its base URL was pointed at the capture endpoint when the sandbox was launched.

Three things are different for these rollouts, and the first is an inversion of the native-agent rule. For blackbox harnesses, holding the connection is the primary mechanism and 503 is the overflow — the opposite of the rule for Gym's own agents. The arithmetic decides it. The Anthropic and OpenAI SDKs inside these harnesses retry a failed request only about twice, so a 503-based pause tolerates only a short stall before the harness's model call errors and the harness fails inside its sandbox. The same SDKs wait roughly ten minutes by default for a response on an open connection, so a held connection is invisible to the harness for any realistic cut. The model server holds blackbox requests up to a hold budget and answers 503 with Retry-After only beyond it. This adds one deployment assumption: every proxy and load balancer on the cross-cluster path must have idle timeouts longer than the hold budget, or a middlebox resets the held connection and manufactures the very failure the hold exists to avoid.

Second, "quiet" replaces "parked". A blackbox rollout has no boundaries, so the prepare poll cannot wait for it to park. Its terminal state for the poll is quiet-at-the-model-server: its last call committed, no new call admitted. The sandbox may keep running tools on the other cluster through the entire pause — the pause gates model calls and nothing else — and the drain deadline never waits for those tools.

Third, the cut treats them as capture-only. During a periodic cut nothing dies: the harness keeps computing, its next model call waits, and when the sentinel clears the call proceeds — provided the pause stayed inside the hold budget. In the checkpoint they are marked non-resumable, because their loop state lives outside Gym; a later restore retries them from scratch as new attempts with new sandboxes. On a shutdown, the harness is left calling a dead endpoint: it exhausts its retries and fails inside its sandbox. The sandbox's compute may sit on a separate CPU cluster, but its lifecycle belongs to Gym's own sandbox API — which upgrades cleanup from leak-and-reap to deliberate: the shutdown sequence terminates the sandboxes of non-resumable rollouts during commit, and the label-query janitor (assumption 6) covers whatever a hard kill missed, at the next startup. The sandboxes kept alive across the gap are those of resumable class-C rollouts, whose reconnect descriptors are in the boundary records.

How does the agent server know a dispatch is a resume, so it does not call /seed_session?

Two signals, and they must agree. The first is the rollout id itself. Resume re-dispatches the same attempt-scoped id the dead attempt used — that is what makes its files, session key, and fingerprints line up — while a from-scratch retry always gets a fresh attempt id. Since the SingleController is the only dispatcher, an id that already has files can only mean one thing: this dispatch continues that attempt. The second signal is explicit: the resume dispatch carries a resume marker with the anchor boundary index, so intent is stated rather than inferred.

On /run entry, before doing anything else, the agent server derives the session-store path from the rollout id — a pure function, so no lookup service is involved — and checks whether boundary records exist. Four combinations, each with a defined outcome:

No records, no marker → a fresh rollout: call /seed_session, write boundary record 0, run normally. Records and marker both present → a resume: skip seeding entirely, select the latest resumable boundary, verify it agrees with the marker's anchor, call /ng-session/restore on each stateful resources server, and enter the loop at the parked position. The conversation itself arrives already rebuilt: the actor built it from the ledger chain plus the anchor boundary's tool results (F4) and passed it as the run input — the records are used to select and verify the anchor and to restore environment state, never to rebuild the transcript, because the thin records deliberately do not carry the model's output items. (The prototype today does the opposite — it rebuilds from its fat records — which is exactly what the G2 thinning replaces.) Marker present but no records → the extraction failed or the assignment is wrong; re-seeding here would silently turn a continuation into a new root that conflicts with the ledger at finalization, so the agent refuses the run and reports non-resumable — the SingleController retries fresh under a new attempt id. Records present but no marker → an id collision or a dispatcher bug; refuse loudly.

One scope note: this machinery belongs to the session tier. In the stripped prototype without boundary records, the environments are stateless by assumption, and re-seeding a stateless session is harmless by definition — the question only becomes load-bearing once /seed_session can allocate real state.

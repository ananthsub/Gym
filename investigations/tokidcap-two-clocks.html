NeMo Gym × NeMo RL · partial rollout checkpointing · resume dataflow

Tokidcap Two Clocks

What resume needs, who owns it, and the exact save/load paths · v3, Aug 24, 2026 · self-contained — companion links at the end · topology verified against NeMo RL main, PR #3407, PR #3456 (branch state 2026‑08‑23), Gym main + PR #2180 head

A killed rollout must resume from its last committed model call, independent of tool/sandbox state. This note lays out the complete resume dataflow — every piece of data a resume needs, its single owner, its save mechanism and location, the join keys, and the exact save and load paths — under the real constraints: per-process virtual environments (the Gym model server cannot import torch or TransferQueue), the Ray-actor hosting topology, and multiple uvicorn workers per server. It then re-evaluates the proposed egress options under the corrected assumption that #3456-style worker staging is the baseline: the vLLM worker persists token ids and logprobs to TransferQueue directly; they are not sent back through Gym.

Supersession notice — Aug 25 An adversarial audit reconciled this page against its newer companion, Checkpoint Choreography, which now governs wherever the two disagree. Superseded here: the boundary record schema (now thin — tool_results + agent_state, no output items); the boundary join key (now the echoed model_call_id, with response_id + fingerprint as witnesses only); checkpoint custody (anchors and file details now live inside an opaque gym_dir the SingleController never reads — not in the SC sidecar); the adopt verb (deleted — restore re-dispatches under the same attempt id and the SC never contacts Gym servers); the single-phase checkpoint(deadline) API (now two-phase prepare/commit(gym_dir)/abort); and the ledger/session storage location (node-local with pack-at-cut, not shared FS). This page remains the record for the storage design rationale, the option analysis, and the scale/tiering arguments.
The settled design, in five lines 1. Per model call, the model server appends one fsync'd row to the rollout's file on node-local disk: the lineage/custody columns, the environment-authored input items, and the completion output items (Variant B′). That single write is simultaneously the durability spine, the multi-worker sharing medium, and the resume record. 2. The vLLM worker stages token deltas + logprobs to TransferQueue before acking; tokens never transit Gym; TQ's staging partition is covered by TQ's own coordinated checkpoint. 3. Nothing "checkpoints" the files — a checkpoint only references them. Storage is tiered: fsync node-local per call; batch byte-range sync to the shared filesystem at rollout completion and at every cut (append-only logs make this a copy-from-offset); the sidecar references only shared-FS-visible state; retention is a rule (nothing referenced by a live checkpoint or an unsealed rollout is ever deleted), the same trust model as the trainer's own checkpoint files. 4. The SingleController's sidecar at each cut records rollout states, attempt ids, resume anchors, and the capture/session directory paths. 5. Resume: the controller re-dispatches; the model server lazily re-reads the rollout's file and rebuilds lineage; the agent's conversation is rebuilt from the stored inputs + completions; prefix supply splices prior calls token-exactly; the regenerated tail call's orphaned staged rows are masked.

Ground rules

Three decisions from the earlier design rounds, restated in full so this document stands alone:

  • Durable-before-ack. A completed model call is made durable before its response is released to the agent. The rollout can then never advance past an unpersisted call, so "last committed call" is always a consistent resume point, with no coordination.
  • Hard-kill correctness first; drain is an optimization. The system must resume correctly after an abrupt death (OOM, node loss, preemption without grace). Any graceful-shutdown protocol only improves resume freshness; it must never be the thing correctness depends on.
  • One durable home per fact; joins, not replication. Each kind of state has exactly one owner and one durable location. Other copies are projections — rebuildable, evictable, clearable. Systems coordinate through join keys, never by synchronizing replicas.

Why the ledger file exists even in staged mode Row #2 is the crux of the whole egress debate. The model server must resolve each request's parent on the serving path, across N uvicorn worker processes, in a venv that cannot read TransferQueue. The ledger file is simultaneously three things: the durable home of custody facts, the process-shared substrate that makes multi-worker parent resolution work (the startup check requires a process-shared lineage store when num_workers>1), and the lazy-load backend for the lineage cache — which keeps metadata for up to 65,536 rollouts in memory and materializes token chains only for a resolved parent, by byte offset, digest-verified. Every "skip the file" proposal must replace all three jobs, not one.
How lineage is built when token ids never reach Gym Parent resolution is text-native, not token-native — it always was. The resolver fingerprints the assistant-authored turns of the request (content, tool calls — canonicalized and hashed), and the model server sees that text in full on every call because the API is stateless: the harness re-sends the whole message list. Matching a new request to the call that produced its prefix is a fingerprint join, tri-state and fail-closed (unique match → token-in continuation; empty/seeded → root; ambiguous → poison). Token ids play no part in it. The ledger row's token-adjacent columns — delta/cumulative lengths, digests, staging key, weight version — arrive as opaque values in the worker's token-free commit coordinates and are recorded without interpretation. On the next call, the resolved result hands the worker the parent's staging-key chain, and the worker — the only party holding tokens — materializes the exact prefix from its local cache or TQ. The code already supports this shape: the lineage cache's metadata-only mode (store_tokens=False, "token arrays stay in the durable log") is precisely "build the DAG without holding ids." Two schema requirements fall out: the worker's prefix-exactness attestation (served prompt extends the parent chain byte-for-byte) must ride back in the coordinates and be recorded per ledger row, since Gym can no longer verify it — finalization checks the chain against these attestations; and cumulative/chain hashes are computed where tokens live (the worker) and stored Gym-side as opaque strings. One operational note: "local cache, else TQ" for prefix materialization needs deliberate rollout→worker affinity (hash of the rollout id), or every re-route turns the else-branch into a TQ read on the hot path.

The save path

The design's central property: checkpoint time is trivial because every save already happened.

Per model call (the only hot path)

  1. Agent POSTs the conversation to the model server (/ng-rollout/{rid}/…/v1/responses).
  2. The model server resolves the parent call (fingerprint match through the lineage cache over the ledger file), mints model_call_id, and appends a durable intent line.
  3. It forwards to the vLLM worker's HTTP endpoint with the capture identity and the prefix requirement — file mode: the parent's exact cumulative token ids; staged mode: the parent's staging-chain keys, which the worker resolves against TQ itself.
  4. The worker generates. Staged mode: it writes the delta row (token ids, mask, logprobs, identity tags) to the TQ staging partition and waits for the ack, then returns text + commit coordinates (the delta ids ride back). File mode: it returns the token bundle on the message body.
  5. The model server appends the commit row to the rollout's ledger and fsyncs — file mode: the full token record; staged mode: the custody row (whether it also carries the delta ids is the one open fork, below).
  6. Only then is the response released to the agent.

Per tool boundary

  1. The resources server exports or snapshots environment state (when stateful).
  2. The agent appends one boundary record — output items, usage, response_id, small env state inline — with one fsync.

At a checkpoint cut

  1. The NemoGym actor syncs every in-flight (and completed-but-unconsumed) rollout's files from node-local disk to the shared filesystem — an incremental byte-range copy (append-only files make "sync" a copy from the last-synced offset), fsync'd on the shared side, truncating any torn final line.
  2. Staged mode: TQ runs its coordinated save_checkpoint, digest-bound to the sidecar.
  3. Only then does the SingleController write its sidecar: group/attempt/reward state plus, per in-flight rollout, the resume anchor — which may only reference state that is shared-FS-visible. An interrupted cut leaves the previous sidecar pointing at the previous consistent set.
Storage tiering (Aug 24) The hot path never touches the shared filesystem: per-call fsync is node-local (the measured +2.29 ms/call baseline applies as-is), and Lustre is written in batches at exactly two moments — rollout completion (hand-off for consumption and GC; the trainer deletes after consuming) and checkpoint cuts (in-flight and unconsumed files). Restore re-seeds node-local storage by copying back down. This is sound because the logs are append-only, idempotent, and monotone: any point-in-time byte-prefix is a valid earlier state, so a stale shared copy is an earlier resume point, never corruption. The rules that keep it correct: files land and fsync on the shared side before the sidecar that references them; anchors only ever point at shared-FS-visible state; torn final lines are truncated at copy or read. The explicit trade: an unplanned node death loses work since the last sync — those rollouts restart from their last shared-FS state or from scratch, correctly — while planned cuts and mere process crashes lose nothing. An optional periodic background sync (every N seconds, same byte-range copy, off the serving path) bounds node-death loss at zero hot-path cost.

At shutdown

  1. Cut (as above), then kill. Optional drain — agents pause between a boundary commit and the next model call — only moves anchors forward. It is never required for correctness.
Scale: hundreds of thousands of in-flight rollouts Per-rollout file size: deltas keep the file O(final context), not O(context²) — roughly the final conversation's JSON plus ~1 KB/call of custody columns. Typical multi-turn tool rollouts land at 100 KB–1 MB; long-context, heavy-tool-output rollouts a few MB. Aggregate bytes are not the problem: 200k in-flight × ~300 KB ≈ 60 GB full state, and a cut ships only deltas since the last sync — tens of GB at worst, seconds of Lustre bandwidth. The problem is file count: per-file sync of 200k small files means ~4 metadata ops each (open/write/fsync/close) — nearly a million MDS operations, minutes of wall time from one process, and abuse of a shared metadata server. The fix is that nothing requires the shared-FS representation to be one file per rollout: pack at the cut. The actor concatenates all per-rollout deltas into a handful of large immutable pack shards (~1–4 GB each, striped, sequential — Lustre's best case) plus an index {rollout_id → [(pack, offset, len), …]} carried by the sidecar. 200k metadata ops become a few dozen large writes. A rollout's shared log is the concatenation of its segments across packs; restore reads the index and extracts only the adopted rollouts, lazily; retirement drops index entries, and packs are GC'd (or compacted) when all their entries are dead. Every invariant carries over unchanged — packs are append-only immutable objects, the sidecar still references only shared-visible state, and the monotone-prefix property still makes any synced state a valid earlier resume point. The node-local per-rollout layout stays exactly as prototyped (it exists for flock granularity and trivial GC); only the Lustre representation changes. At this scale the deployment is also sharded across multiple Gym nodes anyway — each node packs its own shard in parallel. V1 rung: tar -I zstd of the unretired set per cut — full state, self-contained, so retention is "keep the last two archives" with no refcounting; JSON compresses 3–6×, putting even 60 GB of state at a few seconds per cut. Its limits, which define when to move to delta packs: tar re-archives every touched file in full (no bytes-after-offset incrementality, and every in-flight rollout touches its file between cuts), so cut cost scales with total live state rather than progress; and selective restore needs either a full untar (fine — restores are rare) or an emitted member-offset index, which is the pack design with tar as the container. Both rungs share the same sidecar contract and invariants; moving between them is a storage-format change, not a design change. Either way, archive live files with the shipper's read discipline — up to size-at-scan, torn tail handled at the line boundary. Restore-side extraction is the easy direction: it targets local NVMe, where metadata is private and cheap — thousands of JSONLs extract in seconds — and it should run without fsync, because the archive on the shared filesystem remains the durable truth until the next cut (a mid-restore crash just re-extracts). Restore is also re-shardable: rollout files are self-contained, so on a changed node count the SingleController assigns rollouts to the nodes that exist now and each extracts its assigned members.

The one uncovered edge is the tiering trade already stated: a rollout whose file never reached the shared filesystem before an unplanned node death is not resumable — it restarts from scratch, correctly. Every other transition above is idempotent and crash-restartable at any point.

Validated by local prototype (Aug 24): a stdlib-only implementation of this design passes kill-and-resume end to end — multi-turn rebuild, torn-tail resume round trip (parent resolution finds the anchor and the delta on the resumed request), SIGKILL'd writer leaving a clean file, tampered-row fail-closed with automatic fallback to the longest verified chain, two writer processes sharing lineage through flock alone, sub-agent branches excluded from the main-chain rebuild, ambiguity poisoning, tiering node-loss → re-seed → resume with incremental sync. Parallel stress: 4 processes × 50 concurrent commits, 200/200 rows clean. Append+fsync of a ~3 KB row: p50 0.23 ms local. One implementation requirement the tests surfaced: appends must be self-healing — if the file doesn't end in a newline (a predecessor died mid-append), the writer terminates the torn fragment first, or the next commit welds onto it and both rows are lost.

The pause verb

Checkpoint cuts want a quiescent window: if vLLM workers keep staging per-call rows while TQ's coordinated save_checkpoint runs, the snapshot races concurrent puts. First, the honest scoping — the cut is already crash-consistent without a pause, by ordering: every call stages before its ledger commit, files flush before the TQ save, and the sidecar anchors only flushed rows — so every anchored call's staged row is inside the TQ snapshot by construction, and extra rows staged during the save are just orphans that resume masks. What the pause actually buys: (a) it satisfies TQ's snapshot concurrency contract if save_checkpoint is not safe under concurrent puts — a verification item on the TQ side that the pause makes moot; (b) it bounds orphaned work and checkpoint skew. Correctness never leans on it (the hard-kill-first rule is preserved); it is cut-time hygiene.

  • Locate it at the model server, not the agents. The model server is the chokepoint every generation request passes through — including blackbox harnesses that no agent-side drain could ever reach. An admission pause there stops all new dispatches to vLLM with zero agent changes. Backpressure is protocol-native: block briefly, then 503 + Retry-After — OpenAI-compatible clients retry that automatically, so even external harnesses pause themselves without knowing why.
  • Multi-worker mechanics match the house idiom: a flock'd sentinel file in the capture dir, checked per request — one control verb from the SingleController (bearer-authed, restart-surviving) pauses all N uvicorn workers atomically; no cross-process RPC.
  • Two levels, deadline-bounded. Admission pause stops new dispatches; in-flight generations complete, stage, and commit normally, so the drain window is bounded by remaining generation time — budget it against the deadline, and at the deadline proceed anyway (the ordering argument covers the stragglers). If a tighter window is ever needed without waiting out long generations, the second level is a brief sink barrier at the workers: hold stage() during the snapshot itself, letting decoding continue.
  • Piggyback on refit. On-policy training already quiesces generation periodically for weight updates. Aligning cuts with the refit barrier gets the quiescent window at near-zero added stall — the pause verb then only covers cuts that can't wait for one.
  • Cut sequence becomes: pause admission → wait quiet-or-deadline → flush files → TQ save_checkpoint → sidecar write → resume admission. Shutdown is the same sequence without the resume.

This is the earlier drain-verb design in embryo, relocated from the agents to the model server — which covers every harness class at once. The agent-level drain (pause between boundary commit and next model call) remains the later, freshness-maximizing upgrade once boundary markers exist; it composes with, rather than replaces, the admission pause.

The full save sequence under the SingleController

Reconciling the team's checkpoint proposal (Aug 24) with the settled design. Three corrections first, then the merged sequence.

Three corrections to the proposal

1. Each system should pause only the components it started. The SingleController starts the vLLM generation workers, so the SingleController pauses them. The NemoGym actor starts the Gym servers, so the actor pauses those. The proposal instead has a checkpoint request enter Gym and travel through the agent, resources, and model servers out to the generation workers, with acknowledgments coming back along the same chain. Consider what happens when one generation worker is slow or dead: the acknowledgment chain stalls somewhere inside Gym, and the SingleController cannot tell which layer failed — a Gym server, a network hop, or the worker itself. Gym also cannot retry or restart a worker, because workers are Ray actors that only the SingleController manages. The consequence is that every checkpoint failure becomes a two-system debugging session. The fix is to send the two pause commands independently and in parallel: the SingleController pauses its own workers directly, and separately tells the actor to pause Gym. Neither system waits on the other's internal components.

2. Save token ids, never the KV cache — and for the first version, drop in-progress generations. A checkpoint should save the smallest data from which everything else can be recomputed. For a generation in progress, that smallest data is the token ids produced so far. The KV cache is a computation cache over those same tokens: given the tokens, the engine rebuilds the cache by running prefill, which takes seconds per sequence. The cache itself is many gigabytes per node — often larger than the model weights — and its layout changes with engine versions. Saving it turns a checkpoint of megabytes of JSON and token arrays into a checkpoint of hundreds of gigabytes of GPU state, for data that resume can recompute anyway. Separately: a generation that never finished was never returned to the agent, so nothing in the system depends on it. The first version should therefore not save partial generations at all — the resumed rollout re-runs that one call. Saving partial generations is a real feature (it preserves minutes of decoding on very long generations), but it is its own project, not part of this cut.

3. Write the completeness marker last. A checkpoint needs one marker that means "this checkpoint is complete and safe to restore from", and restore code must look for that marker first. The proposal creates training_info.json at step 4, before the model save, the TQ save, and the Gym file sync have run. Suppose the job is killed while those saves are half done — for example, TQ state saved but the Gym archive did not. On restart, the restore code finds training_info.json, concludes the checkpoint is complete, and then either fails or silently proceeds without the Gym files. The fix: create the temporary directory early, write every part into it, write training_info.json only after every part has landed, and finish with an atomic directory rename. The rename is the moment the checkpoint exists.

The alternative proposal — shut the workers down and let Gym react to error responses — should be rejected. Gym should stop sending generation requests because it was asked to stop, not because requests started failing. Walk through what the error-driven version does: the workers begin checkpointing and start returning errors; Gym has hundreds of requests in flight and thousands more about to be sent; every in-flight request fails; Gym's HTTP client retries each failure three times with backoff, hammering the checkpointing workers; the model server cannot tell whether the workers are checkpointing (so it should wait) or have crashed (so it should fail the rollouts); and external harnesses see their calls fail and apply retry behavior we do not control. An error response carries no intent — it means "something is wrong", not "please wait". The consequence is that every checkpoint exercises every error path in every client, and real failures hide inside checkpoint noise. The fix is an explicit pause command flowing down the same path as everything else: SingleController → actor → model server. A checkpointing worker may still return a clean error to a late-arriving request as a safety net, but that error is never the coordination mechanism.

The merged sequence

  1. Fence dispatch. The SingleController pauses the rollout and train pumps so no new rollout can start. The NemoGym actor then confirms that every rollout already dispatched has actually arrived in Gym. After this point, the set of in-flight rollouts is fixed and known. (Proposal steps 1–3, kept as written.)
  2. Start the independent saves early. The SingleController creates the temporary checkpoint directory and starts the model+optimizer save asynchronously. This save touches only trainer state, so it depends on nothing that follows and can overlap with all of it. (Proposal step 5, kept.)
  3. Pause new generation requests. The SingleController calls checkpoint(deadline) on the actor. The actor sets the model server's pause flag — a file in the capture directory that all uvicorn workers check, so one write pauses all of them. New requests from agents receive a retry-later response with an explicit retry time; OpenAI-compatible clients honor it automatically. Generations already running finish normally: each one stages its tokens to TransferQueue and commits its row to the rollout file, exactly as during normal operation. If a generation has not finished by the deadline, it is abandoned — it was never returned to an agent, so nothing depends on it, and the resumed rollout will re-run that call.
  4. Finish tool work and snapshot environments session tier only. When boundary records exist, agents finish the tool calls already in progress, resources servers snapshot their state (or record a sandbox reconnect descriptor), and each agent writes a boundary record pairing the conversation position with the environment state. When boundary records do not exist yet, skip this step entirely: without a record to capture the tool outputs, waiting for tools to finish preserves nothing, and resume starts from the last committed model call either way.
  5. Run the three remaining saves in parallel. The SingleController saves TransferQueue state; the model+optimizer save from step 2 continues; the actor packs the unretired rollout files into one compressed archive and writes it to the shared filesystem. These three can overlap safely because generation is paused — nothing is writing to TransferQueue — and the rollout files never touch TransferQueue at all.
  6. Commit. The SingleController writes the manifest that binds all parts together — the trainer checkpoint, the TransferQueue checkpoint digest, the archive paths with their synced lengths, and each rollout's resume anchor — and then atomically renames the temporary directory. For a periodic checkpoint, it then resumes the pause flag and the pumps. For a shutdown, it kills the job here.

Who calls the pause, exactly

The processes involved: the SingleController is a Ray actor in NeMo RL. The NemoGym actor is another Ray actor; when it starts, it launches the Gym servers — head, agent, model, resources — as ordinary OS subprocesses on its own node. The model server subprocess runs N uvicorn worker processes behind one port. Because the actor and the Gym servers share a node, they share a filesystem, and the actor already holds HTTP clients to the Gym servers (it uses them to dispatch /run requests today). The pause flow:

  1. The SingleController calls nemo_gym_actor.checkpoint.remote(deadline) — a Ray method call, the same mechanism it uses for everything else it asks the actor to do.
  2. Inside checkpoint(), the actor sends POST http://localhost:<model_port>/control/pause with the bearer token. This is one HTTP request that lands on one uvicorn worker.
  3. That worker writes the pause sentinel — an atomic file create inside the capture directory. The file is how one request pauses all N workers: every worker stats the sentinel at the top of each request handler, so the other N−1 workers see the pause on their very next request. The actor could write this file itself, since it shares the filesystem, but routing it through the HTTP endpoint keeps the file layout private to the model server and gives standalone Gym deployments the same API.
  4. A paused model server handles an incoming generation request in one of two ways. For in-cluster callers (Gym's own agent servers), it holds the request — the async handler awaits the resume event — because Gym's internal HTTP client retries only three times with backoff, and a pause longer than that budget would otherwise surface errors into agent loops. For external harnesses, or when a hold exceeds a threshold, it returns 503 with Retry-After, which OpenAI-compatible clients obey automatically.
  5. The actor then polls GET /control/status until the in-flight count reaches zero or the deadline passes. The in-flight count needs no shared memory between workers: an admitted call writes an intent line to the rollout file at admission and a commit row at completion, so "in flight" is exactly the number of intents without commits, countable from the files by whichever worker serves the status request.
  6. On resume(), the actor calls POST /control/resume; the handler deletes the sentinel; held requests release and retried requests succeed.

What a boundary is, exactly

An agent server's /run loop does the same four things repeatedly: send the conversation to the model server; receive a response; if the response contains tool calls, execute them against the resources server; append the tool results to the conversation. A tool boundary is the moment between appending the tool results and sending the next model call. At that moment, and only at that moment, the conversation and the environment agree: every tool effect that has happened is also recorded in the conversation. Boundary k is that moment after the k-th round of tool execution; boundary 0 is after seeding, before the first call. This is why boundaries are the safe save points and mid-loop moments are not: between sending a tool call and appending its result, the environment has changed in ways the conversation does not yet reflect.

The session tier is three concrete changes, all present in the session-state-prototype branch. First, agent servers write a ToolBoundaryRecord at each boundary — output items, usage, the serving response_id, and the environment state — and their /run becomes resumable: re-dispatched with a known rollout id, it reads the records, truncates to the last resumable boundary, rebuilds the conversation, and continues. Second, resources servers implement two hooks, export and restore: a server holding pandas DataFrames in memory returns their serialized form from export; a server wrapping a sandbox returns a reconnect descriptor; a server that can do neither declares itself unsupported and its rollouts restart from scratch rather than resuming. Session identity is a pure function of the rollout id, so a restarted server process re-derives the same session key and a restore lands in the right session. Third, the commit order is fixed: the environment snapshot is persisted first, the boundary record that references it is appended second — so a boundary record's existence guarantees its snapshot exists. The one genuinely new API for the checkpoint story is POST /control/drain(deadline) on the agent server: it sets a flag that each active /run loop checks at its boundary point, and a loop that reaches a boundary while the flag is set commits the record and waits instead of sending the next model call. NeMo RL never calls a resources server: the SingleController talks to the actor, the actor talks to the agent and model servers, and the agent server drives the resources servers — because only the agent knows when a boundary has been reached.

The load path

  1. The trainer restarts. The SingleController loads its sidecar; staged mode also runs TQ load_checkpoint and reconciles expected staging keys against what the store actually holds (counting — partial key misses return fewer rows without error).
  2. The SingleController explicitly re-spins the NemoGym actor (max_restarts=0 fits this: restarts are always deliberate). Before starting the Gym servers, the actor re-seeds node-local storage: it copies the sidecar-referenced rollout files down from the shared filesystem into the local capture dir. The lineage store's cursor-reset machinery absorbs the changed inodes — a re-seeded file just reads as a fresh backend.
  3. For each unsealed rollout marked resumable, the SingleController issues an adopt call to the model server — new attempt id, authorized by the durable control token, targeting the recorded anchor.
  4. The model server needs no state pushed into it: its lineage store lazily reads the rollout's ledger file on first touch (metadata into the cache; token chains only if and when a parent resolves).
  5. The agent's /run is re-dispatched with the resume flag: it truncates the session record to the anchor boundary, rebuilds the transcript from boundary records, and the resources server restores the environment snapshot (or reconnects the sandbox descriptor).
  6. The first continued model call resolves against the rebuilt lineage and gets its exact prefix — file mode: cumulative ids from the ledger; staged mode: staging-chain keys against the restored TQ rows. The worker verifies the served prompt extends the prefix exactly; continuation is bit-exact.
  7. At seal, delivery proceeds normally: staged mode — the finalizer fetches the chain's staged rows, verifies, and publishes the group's train rows; file mode — the builder freezes the JSONL into the rollout payload. Retirement after consumption triggers file/staging-key GC; anything referenced by a still-live checkpoint is pinned.
Rebuilding the conversation on load Request/response correlation is free by construction: each row pairs a call's input delta with its output items, written in one atomic append at commit — there is no separate tracking to reconcile. Chain order comes from parent pointers, not file order (concurrent sub-agent calls interleave in the file). The rebuild, given the anchor call from the sidecar:
  1. Read the rollout's rows — last row wins per call_id, torn tail dropped. Rows with an intent but no committed row (in-flight at the kill) are excluded and masked.
  2. Walk parent_call_id pointers back from the anchor to the root — this selects the main chain out of the DAG.
  3. Concatenate forward: input_delta(root) · output_items(root) · input_delta(c₂) · output_items(c₂) · … · output_items(anchor). Each input delta is exactly the environment/user-authored items between calls, so the interleaving reproduces the conversation as of the anchor's response. For native agents everything is Responses items end-to-end — pure concatenation, zero conversion — and the result drops directly into responses_create_params.input.
  4. Verify while walking: recompute the assistant-turn fingerprint of the rebuilt prefix at each step and compare it against the parent fingerprint the next row recorded at admission. Any disagreement fails closed to whole-rollout retry. This re-embedding step carries no new assumption — serving output items and matching them when the harness re-embeds them in its next request is exactly the round trip the fingerprint join already validates on every live call.
The delta itself costs nothing to extract at write time: admission already verifies that each request extends the parent's conversation, so the delta is the suffix beyond the verified prefix — a byproduct of the check that runs anyway. The remaining loss window is unchanged: environment turns that completed after the anchor's response but never arrived in a request exist nowhere and are regenerated.

The proposed options, re-evaluated under the corrected assumptions

Corrections applied: the relay carries only a token-free text receipt (tokens and logprobs go worker→TQ and never return to Gym); the NemoGym actor is max_restarts=0, so its death is loud, not silent; and worker staging is the baseline, not an alternative.

O1aPer-call text receipt → actor → TQ unnecessary hop

With tokens out of the payload, the earlier serialization critique mostly evaporates — the receipt is small. What remains is that the hop delivers data that has to exist locally anyway and can be pulled on demand:

  • The model server must keep process-shared custody/lineage state for its own serving path regardless (inventory row #2) — the receipt push doesn't replace the ledger, it copies from it.
  • #3456 already assembles receipts by pulling the manifest from the model server at seal. Pull-from-durable-truth beats push-per-call: a push can be lost in flight and must be idempotently retried; a pull re-reads the ledger whenever it's needed — at seal, at a cut, or never.
  • Conversation text cannot ride this path into TQ anyway — the staging and finalizer schemas structurally reject content fields by design. The transcript a resume actually replays comes from session-store boundary records (row #3).

Synchronous, the hop adds an actor-liveness dependency to every model call; asynchronous, it adds a loss window — for a copy of data whose truth is durable a fsync away. The pull model needs neither.

O1bActor-side queue + drain, with max_restarts=0 loud loss is still loss

The fix is real: with restarts disabled and spinup explicit, an actor death fails the run visibly instead of silently swallowing queued receipts. But the queue's contents are still gone — rollouts whose receipts existed only there cannot resume — and the actor is now a run-wide single point of failure on a per-call path it previously wasn't part of. The deeper question stands: a queue exists to buffer pushes, and nothing here needs a push. The durable ledger plus pull-when-needed has no queue to lose.

O1cFlush custody state at shutdown only coherent, but pays more than the file it avoids

Corrected reading: tokens and logprobs are already in TQ per call (worker staging) — so a shutdown flush would carry only custody metadata, and much of the call DAG is even re-derivable from TQ row tags (rollout, call, parent, lengths, digests). This makes O1c coherent. What it still costs, against the ledger file it's trying to avoid:

  • Multi-worker parent resolution loses its substrate. During the run, N uvicorn workers share lineage through the ledger file. RAM-only custody means single-worker model servers or new shared-memory machinery — a bigger change than the file it removes.
  • Adopt becomes TQ-dependent and push-based. A restarted model server cannot read TQ, so an RL-venv process must read the tags and push seed state in — a new protocol, replacing a lazy local file read that already exists.
  • Unplanned deaths still lose what tags don't carry: admission decisions, fingerprint state, terminal witnesses — plus everything for rollouts whose flush never ran.
  • The memory story, stated precisely: the file-backed lineage cache holds metadata only for up to 65,536 rollouts and lazily materializes token chains from the file by byte offset. That design is cheap because a locally readable backend exists; file-less custody gives the lazy loads nowhere to go.

And the flush itself is drain machinery promoted to a correctness requirement — whereas with the ledger, shutdown is a no-op.

O2The model-server ledger file the spine, both modes

One append+fsync per call at commit (measured +2.29 ms/call p50 on local disk; the Lustre number is the open measurement). In file mode it carries full token records; in staged mode, custody rows. It is three mechanisms in one file: durable custody home, multi-worker sharing substrate, lazy-load backend. File count is bounded by in-flight rollouts plus consumption lag (files are deleted at retirement, pinned while a checkpoint references them). Delta records keep long-multi-turn rollouts linear rather than quadratic.

O6′Restore-time re-stager the useful remnant of the shipper idea

The original shipper (actor continuously tails files into TQ) is moot in staged mode — the worker already puts once per call, and nothing else should; there is no second stream of TQ traffic to create or to optimize away. The one moment a file→TQ copy earns its keep is restore, and only in the token-bearing fork below: if the ledger carries the deltas, an RL-venv process re-stages just the adopted rollouts' chains into TQ at restore — bounded work (in-flight count × chain length, once, off every hot path) — and the staging partition then never needs to be part of the TQ checkpoint at all.

Variant A vs Variant B — the two live step-by-step proposals

Both walkthroughs (Aug 24) share the entire spine: stateless agent re-sends the full conversation; the model server fingerprints assistant turns and resolves the parent in the lineage JSONL under flock; dispatch carries text + identity only; the worker splices the parent prefix from its cache or TQ, stages the delta before acking, and returns text + token-free coordinates; the model server appends the lineage row before releasing the response (the publication point — a later call can only then resolve it); finalization pulls the token-free manifest, verifies, linearizes staged rows, and clears. The only difference is where the transcript text goes.

Is the transcript necessary at all?

For the training pipeline the walkthroughs describe: no, provably. Trace every consumer through the 18 steps. Parent resolution (steps 2, 11) hashes the incoming request and compares against fingerprints already stored in lineage rows — stored text is never read. Context-digest verification: hashes again. Prefix supply (steps 13–14): staging-key chains and token ids, never text. Finalization (step 18): the token-free manifest plus staged token rows — the finalizer structurally rejects text fields. Delete steps 3, 8, and 12 from both walkthroughs and every training-correctness property is unchanged.

For crash-resume, with boundary markers deferred to a follow-up: a conversation record is necessary — but only half of one. The resumed agent must re-send the conversation, and after a kill the harness's memory is gone. Split the conversation by author:

  • Environment/user-authored turns (tool outputs, user messages) are irreducible. They exist token-side only as rendered prompt-delta tokens, and recovering structured items from rendered template text is template inversion — fragile and rejected. If they aren't stored as text, they are gone. This is the part of the transcript that is genuinely necessary, and it is exactly what steps 3 and 12 append.
  • Assistant-authored turns are recoverable from the staged tokens. Detokenizing a generation span is exact (no template inversion — it's the model's own output), and parsing tool calls out of generated text is precisely what the serving path already does. But the recovery runs only in an RL-venv process against live-or-restored TQ — so storing completions too keeps the resume read Gym-local and independent of the data plane, which is this document's third ground rule. Recommended, not required.

What resume looks like with this per-call record and no boundary markers: resume at the last recorded request. Rebuild the conversation as seed (the re-dispatched task row) + stored input deltas + completions; re-dispatch the tail call; prefix supply splices calls 1…k−1 token-exactly; the dead attempt's staged rows for the regenerated call are orphaned and masked. This never mixes old observations with re-run tools — the kept prefix embeds only stored observations — so it is sound for stateless environments; at most one call's work (the tail call and its tool executions) is lost. The boundary-marker follow-up then improves freshness by at most that one call and adds the environment-state pairing that stateful servers need — and the input-delta record built now is the embryonic boundary record: same content, re-keyed per boundary with the response_id anchor. Nothing is thrown away.

Verdict: keep steps 3 and 12 as an inputs append (the necessary half), keep step 8 if you want resume reads self-contained in the Gym venv (recommended), and store it as the JSONL — never through TQ. The table above is the reason: the TQ route adds a proxy, a queue, a drain thread, a text partition in a tensor store that no existing consumer reads, and an RL-venv restore path — while making the one invariant that matters ("no published call without its inputs durable") unachievable, since fire-and-forget can always leave holes precisely in the record whose one critical consumer, resume, cannot tolerate them. As B′: fold the text columns into the ledger's commit append — one row, one fsync per call. For blackbox harnesses none of this enables resume (their loop state lives outside Gym); their transcript value is diagnostics, which evaluation capture on main already provides.

Step-level corrections that apply to both walkthroughs: (1) the staged delta must be rendered_prompt[prev_len:] + generated — it includes the tokenized environment-authored turns, not only "output tokens", or linearization has gaps; the mask distinguishes carried from generated. (2) The lineage-append-before-release ordering is load-bearing — keep it stated as an invariant, not a step. (3) "Local cache, else TQ" prefix loading needs deliberate rollout→worker affinity; TQ makes no documented cross-client read-after-write promise, so the else-branch should be a cold path. (4) "Clears all rollout stores" at finalization must except anything referenced by a still-live checkpoint (adopted/partial rollouts). (5) Freshness honesty: with a token-free ledger, resume freshness is bounded by the last TQ checkpoint in either variant — the tokens for the kept prefix must exist in TQ at restore. Variant B's continuous transcript still pays off in integrity and in enabling the token-bearing upgrade below, which is the actual freshness lever.

The B′ walkthrough — updated steps

The original Variant B walkthrough, updated to the settled design. Differences from the original: old steps 3, 8, and 12 (separate messages-JSONL writes at request arrival and response) are merged into the single commit append; the append is self-healing and node-local with the fsync-policy knob; and the lifecycle steps (completion, cut, restore, resume) are now explicit.

Call 1

  1. Agent → model server: POST /ng-rollout/r42/training-token-capture/v1/responses with the full task prompt. The rollout id in the path is the capture key everywhere.
  2. Model server resolves the parent: hashes the assistant-authored turns, reads the rollout's file under shared flock (cursored cache). No rows → root call; parent null; the input delta is the entire request.
  3. Model server dispatches to the vLLM worker: text + capture identity (rollout id, call id c1, parent null). No token arrays on this hop.
  4. Worker renders and generates; before acking, stages the call's delta — token ids (rendered prompt + generated), mask, logprob delta, router indices — to rollout_staging keyed r42/c1. Synchronous, durable-before-ack at the worker.
  5. Worker → model server: text + token-free coordinates (staging key, prev/delta/cum lengths, digests, weight version). Token ids never ride back.
  6. The commit: one self-healing append to the rollout's node-local file, fsync per policy — a single row holding the custody columns (call id, parent, fingerprint of the served turn, staging key, lengths, digests), the input_delta (request items as received), and the output_items (served response items). This one write is simultaneously the durability event, the cross-worker publication (any uvicorn worker can now resolve c1), and the resume record.
  7. Only then does the model server return the token-stripped response to the agent.
  8. The environment executes the returned tool calls; the harness appends the results to its in-memory conversation.

Call 2

  1. Agent re-sends the full conversation, now including c1's assistant turn and the tool results.
  2. Model server resolves: the trailing assistant turns fingerprint-match c1's recorded served fingerprint; the extension check verifies the request extends c1's conversation; parent = c1, token-in admission — and the input delta is the suffix past the verified prefix (the tool results), extracted as a byproduct of the check that runs anyway.
  3. Dispatch to the worker with a parent reference — the staging-key chain — never tokens.
  4. Worker splices the exact parent prefix from its local cache (rollout→worker affinity) or TQ, generates, stages delta 2 pre-ack.
  5. Worker returns text + coordinates for c2.
  6. Model server commits row c2 (same single append), returns text to the agent. Any worker serving call 3 resolves c2 → c1 from the shared file.

Lifecycle

  1. Completion: /run returns; the actor syncs the rollout's file up to the shared filesystem (byte-range from last-synced offset); finalization pulls the token-free manifest, the finalizer fetches and verifies the staged rows and publishes the group's training rows; after the trainer consumes, the actor retires the rollout — staging keys and both file copies deleted, pinned while any live checkpoint references them.
  2. Cut: the actor syncs every unretired rollout file node-local → shared (incremental, torn tail excluded, fsync'd on the shared side); staged mode runs TQ save_checkpoint; only then does the SingleController write its sidecar {rollout → shared path, synced_len, anchor}.
  3. Restore: sidecar load; TQ load_checkpoint; the actor re-seeds node-local files from the shared copies (verifying length ≥ synced_len); the model server starts cold and lazily re-reads files on first touch — cursor-reset absorbs the new inodes.
  4. Resume: for each resumable rollout the actor rebuilds the conversation from the file — walk parent pointers from the anchor, concatenate input_delta · output_items, verify the fingerprint chain, fail closed on mismatch — and re-dispatches the task with the rebuilt conversation as responses_create_params.input. The harness doesn't know it's resuming: its first call arrives and fingerprint-resolves to the anchor exactly as in step 10; the dead attempt's post-anchor staged rows are orphaned and masked.

Extension: tailing to TQ via the NemoGym actor

Build only when a TQ consumer for these rows exists — none does today. The actor is TQ-capable (RL uv.lock venv) and sits on the Gym node; the file remains the single truth and TQ rows are a derived projection; the model server never learns the shipper exists.

  1. The actor runs a tail loop over the capture dir: per unretired rollout file, a cursor {inode, byte offset}. Cursor persistence is an optimization — on restart it can always rebuild by re-reading.
  2. Each tick reads complete lines from the cursor to EOF (torn tail excluded, same reader rule) and parses rows.
  3. Per new committed row it derives the TQ record and does an idempotent put keyed {rollout_id}/{call_id} into a transcript partition. At-least-once delivery + keyed dedup = effectively exactly-once.
  4. The cursor advances only after the TQ put is acked. A crash between put and advance re-puts on restart and dedups by key.
  5. Backpressure never touches the serving path: if TQ is slow or down, the shipper lags; lag = EOF − cursor, exported as a metric; the file keeps growing on local disk and nothing blocks.
  6. Retirement interplay: the actor is also the retiring party, so policy is one comparison — if the TQ copy must complete before deletion, retire waits for cursor = EOF; if best-effort, retire deletes and drops the cursor.
  7. Restore interplay: after re-seed the cursors reset with the new inodes; re-shipping from offset zero is safe (keyed dedup), or synced_len bounds where shipping resumes.

Anatomy of one tick (an adaptive poll loop in the actor — sleep the interval only when caught up, re-tick immediately while behind): enumerate the active rollout set from the actor's own dispatch state (no globbing); detect per file via stat() — inode change means re-seed, reset the cursor; snapshot-read the byte range [cursor, size) under shared flock held for the memory copy only, never across a TQ put, then trim at the last newline (a torn tail waits one tick); parse — a mid-stream parse error is corruption: alert and stop that rollout loudly, never skip silently; batched put of all derived records across all files this tick, keyed {rollout}/{call}; advance cursors only after the ack, so a crash between put and advance re-ships once and dedups. The tick interval controls exactly one thing — the staleness of the TQ projection (the lag metric EOF−cursor) — and nothing else: not durability (the commit fsync already happened), not correctness (nothing consumes the projection on a critical path), not the serving path (the flock is held for a copy).

Recommendation: token-bearing, contingent on the fsync measurement. If the target filesystem makes the larger fsync expensive, fall back to token-free and accept the TQ-checkpoint dependency — the load path above works either way; only steps 1 and 6 change flavor.

Measurements that decide the remaining knobs

  • Cut-time flush cost under tiering: in-flight rollout count × file size, as incremental byte-range copies to the shared filesystem, against the checkpoint grace budget. (The per-call Lustre-fsync measurement is moot under tiering — the hot path fsyncs node-local, where +2.29 ms/call is already measured. Token-bearing vs token-free row sizes now matter only for this batch copy, weakening that fork's one cost argument.)
  • TQ save_checkpoint/load_checkpoint wall time for a realistic staging partition — this prices the token-free fork's restore dependency.
  • Manifest-pull latency at cut time for in-flight rollouts (the receipt path O1a wanted to pre-populate) — expected trivial, worth confirming at fleet scale.

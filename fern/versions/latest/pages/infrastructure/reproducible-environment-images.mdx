# Reproducible Environment Images

NeMo Gym can turn a resolved environment configuration into immutable build inputs and OCI images. The workflow separates authored configuration, dependency resolution, image construction, and runtime configuration so that credentials and deployment addresses do not become part of an image.

<Warning>The runtime can operate without package installation or dataset downloads, but an environment may still require network access to model APIs, external tools, or other Gym servers. Inspect the selected components before applying an egress policy.</Warning>

## Create the environment lock

Resolve the same environment, agent, resources server, and model configuration that you plan to deploy. Strict locking rejects dependency index directives, mutable VCS references, credentials in URLs, and generated requirements without hashes.

```bash
gym env lock \
  --environment my-environment \
  --model-type openai_model \
  --base-image registry.example.com/gym-base@sha256:<digest> \
  --source-root "$PWD" \
  --platform linux/amd64 \
  --strict \
  --output build/lock
```

The command writes `build/lock/environment.lock.json`. The lock records the digest-pinned base image, target platform, copied Gym source digest, exact Python and `uv` versions, resolved configuration digest after secret-shaped values are masked, component source closure, and hash-complete requirements for every selected runtime component.

Gym infers transitive source dependencies from imports rooted at `resources_servers`, `responses_api_agents`, and `responses_api_models`. A component can declare dynamic source dependencies and argv-based build steps in `component.build.yaml`. Changing selected source, source dependencies, build metadata, or Gym runtime source after locking causes image construction to fail.

## Build one packed image

The packed image contains the Gym CLI and every component environment in the lock.

```bash
gym env build-image \
  --lock build/lock/environment.lock.json \
  --source-root "$PWD" \
  --tag registry.example.com/gym/my-environment:<tag> \
  --platform linux/amd64 \
  --load
```

The build uses the base image recorded in the lock. Strict locks require an OCI digest instead of a mutable tag. Image construction verifies the copied Gym source, target platform, Python version, and exact build-stage `uv` version. It installs each component's hash-complete requirements directly with `uv pip install --require-hashes --no-deps`.

The final image runs as numeric user `65532`. It sets `NEMO_GYM_RUNTIME_INSTALL_POLICY=require-existing`, so mounted configuration cannot weaken the policy. Gym refuses to create a missing virtual environment and never invokes `uv` or `pip` through component environment setup at runtime.

<Warning>Some existing components install external tools or download assets in their own startup code. `component.build.yaml` moves declared setup into image construction, but a component is not offline-certified until its startup path has been tested with networking disabled. Check `gym env capabilities`; `offline_runtime_installation` remains `false` while the catalog still contains unconverted startup installers.</Warning>

## Prepare immutable task data

Collate or otherwise prepare the input JSONL before creating its artifact. The artifact command canonicalizes each row, assigns a stable `task_id` when one is absent, and writes a digest-addressed directory.

```bash
gym eval prepare-artifact \
  --input build/prepared/benchmark.jsonl \
  --output-dir build/artifacts \
  --split benchmark \
  --environment-lock build/lock/environment.lock.json
```

Mount the resulting digest directory into the runtime and pass it to evaluation:

```bash
gym eval run \
  --environment my-environment \
  --model-type openai_model \
  --split benchmark \
  --prepared-artifact /artifacts/<artifact-digest> \
  --environment-lock /opt/nemo-gym/environment.lock.json \
  --output /results/rollouts.jsonl
```

Gym verifies the manifest identity, normalized data digest, canonical row encoding, row count, split, and environment-lock identity before starting servers. `input_sha256` records the original JSONL bytes as provenance, while `data_sha256` and the artifact identity describe normalized task content. When `--prepared-artifact` is set, the end-to-end path does not download or collate task data.

## Inject runtime configuration

Do not add API keys, tokens, service addresses, or prepared data to the build context. Write the fully resolved runtime configuration to a read-only mounted file and point Gym at it:

```bash
docker run --rm \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=4g \
  --mount type=bind,src="$PWD/runtime.yaml",dst=/run/nemo-gym/runtime.yaml,readonly \
  --mount type=bind,src="$PWD/results",dst=/results \
  --mount type=bind,src="$PWD/artifacts",dst=/artifacts,readonly \
  --env NEMO_GYM_CONFIG_FILE=/run/nemo-gym/runtime.yaml \
  registry.example.com/gym/my-environment:<tag>
```

The packed runtime needs writable locations for temporary files, Ray state, caches, and result artifacts. The image defaults these temporary paths under `/tmp`; mount a bounded `tmpfs` or writable volume there. Mount output locations separately when results must persist.

`NEMO_GYM_CONFIG_DICT` takes precedence over `NEMO_GYM_CONFIG_FILE` when both are set. Prefer the file form in orchestrated deployments because secret managers can project it as a read-only volume, and leave `NEMO_GYM_CONFIG_DICT` unset.

## Build split server images

Split mode publishes one foreground head-server image and one foreground image for each locked component. Because the command records registry digests, it always pushes the generated images.

```bash
gym env build-images \
  --lock build/lock/environment.lock.json \
  --source-root "$PWD" \
  --repository registry.example.com/gym/my-environment \
  --platform linux/amd64 \
  --output build/composition.bom.json
```

`composition.bom.json` maps every configured server instance to an image reference containing an OCI `sha256` digest. It does not contain service addresses or credentials. Render and validate a deployment contract before passing the split images to an orchestrator:

```bash
gym env render-launch-plan \
  --config runtime.yaml \
  --bom build/composition.bom.json \
  --lock build/lock/environment.lock.json \
  --output build/launch-plan.json
```

The renderer rejects unknown schemas, lock/BOM identity mismatches, mutable image references, missing or duplicate head images, incomplete instance coverage, unsafe entrypoints, and invalid or duplicate ports. The output describes image references, commands, arguments, a read-only configuration mount, environment variable names, ports, dependencies, and the external Ray requirement. It contains no runtime configuration values and does not launch containers.

## Compatibility contract

Run `gym env capabilities` to inspect the protocol and schema versions implemented by the installed Gym build.

The initial contract has these guarantees:

- `nemo-gym/runtime/v1` identifies the runtime startup, file-based configuration, immutable-install policy, and image-label contract.
- `nemo-gym/environment-lock/v1`, `nemo-gym/prepared-artifact/v1`, `nemo-gym/composition-bom/v1`, and `nemo-gym/launch-plan/v1` identify their JSON document shapes. Consumers reject an unknown schema version instead of guessing.
- Strict locks require a digest-pinned base image. Image construction also verifies the target platform, copied Gym source, Python version, and exact build-stage `uv` version. An external Ray cluster must use the exact Ray and Python versions recorded by the lock.
- An image is compatible with a lock only when its `io.nvidia.nemo-gym.lock.digest` label equals the lock identity. Split images additionally identify their component and source content digest through the composition BOM.
- Passwords, secrets, credentials, authentication fields, cookies, private headers, tokens, and keys are masked before configuration digests are calculated. Deployment hosts, ports, URLs, addresses, and endpoints are also excluded from lock identity. Runtime configuration values are not serialized into locks, images, BOMs, or launch plans.
- Gym's component environment setup cannot install packages in a strict image runtime. Declared component build steps run during image construction and verify their expected outputs. Undeclared setup inside component startup code remains component-specific, so the capabilities document does not claim general offline runtime installation.
- A prepared artifact tied to an environment lock can run only when the runtime supplies the same lock. A strict image embeds its lock path in `NEMO_GYM_ENVIRONMENT_LOCK`.

An incompatible behavior or document-shape change requires a new protocol or schema version. Additive implementation fixes that preserve the documented behavior remain within version 1.
